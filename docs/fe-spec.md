# FE 기능명세서

## #95 인증·동의·소유권 통합 — 운영 BLOCKED

합성 Extension에 인증·정책 확인·명시적 동의·전체 철회 UI를 구현했다. Token은 trusted-context session storage만 사용하고 서버 재검증·로컬 owner/consent 바인딩·계정 전환 Queue 차단·철회 원본 보존을 적용한다. production v1 Popup에는 운영 등록이 준비되지 않았다는 안내를 추가했다. 실제 참여자 로그인/동의 확보를 완료한 것은 아니다.

상세 구현·테스트·미충족 조건은 [#95 통합 검증 보고](v2-auth-consent-integration-validation.md), 새 DTO는 [인증·동의 API](contracts/auth-consent-api.md)를 따른다. **P1~P6 PROPOSED, P2/P6 BLOCKED, 전체 삭제 증거 없는 PURGED 금지 유지.** 아래 선행 작업의 미구현 설명은 해당 작업 당시 기록이다.

## #93 개인정보 회수 구현 — 합성 검증 / 운영 BLOCKED

v2 RetractionEntry는 request 원본·phase·attempts·retry 시각·ACK를 기존 v2 aggregate에 additive 저장한다. 일반 Queue/ACK와 별도이며 보내기 전 sending Commit, 응답 후 ACK Commit, 같은 ID 재전송·재시작 복구를 한다. compacted 방문 ID도 포함하며 새 세션에는 이전 ID를 넘기지 않는다. QUARANTINED/PURGED 응답 어느 쪽도 로컬 hold·수집·END drain을 해제하지 않는다. production v1 진입점과 IndexedDB v1 값은 유지한다.

상세 구현·삭제/격리 Inventory·명령·실패/미검증 범위는 [개인정보 회수 검증 보고](v2-privacy-retraction-validation.md)를 따른다. 아래 과거 작업의 미구현 설명은 당시 기록이다. **P1~P6 PROPOSED, P2/P6 BLOCKED 유지.**

## #91 FE 합성 전용 구현 — 승인 변경 없음

FE의 v1은 기존 1초/후보 종료 순서 수집을 유지한다. #91의 v2 수집기·5초/4초/5분·IndexedDB/ACK/END_PENDING·상태 어댑터는 별도 합성 확장 진입점으로 구현했다. production popup/background에는 v2 설정이나 활성화 경로가 없다.

실제 구현·명령·Mock/Chrome/HTTP 구분·미구현/미검증 범위는 [FE v2 검증 보고](fe-v2-collection-validation.md)를 따른다. **P1~P6 PROPOSED, P2/P6 BLOCKED 유지.** 아래 과거 작업의 미구현 설명은 각 작업 당시 기록이다.

> Issue #79 정책을 반영한 목표 명세다. 기준 코드 `6e15dd3`에는 세션·수집·전송·복구가 구현되어 있으며 v2는 미구현이다. 확정/제안 구분·타입·API는 [수집 규격](data-collection-spec.md)과 [공통 계약](data-analysis-contract.md)을 따른다. 기존 기능 ID를 유지한다.

## 1. 문서 개요

본 문서는 `FE-001.md`부터 `FE-010.md`까지의 기능 정의를 통합한 프론트엔드 기능명세서이다. 기존 기능 ID와 요구사항을 유지하고 공통 동작 규칙, BE 연동 관계, 완료 조건 및 구현 전 확정 사항을 정리한 문서이다.

FE는 Chrome Extension에서 최초 작업 목표를 입력받고 작업 세션을 관리하며, 세션 중 분석 대상 페이지의 정보와 탐색 행동을 수집하는 영역이다. BE의 최종 판단이 DRIFT이면 최초 목표를 다시 제시하고 사용자의 선택을 기록하는 역할이다. 사용자 비교 평가를 위한 고정 주기 목표 알림도 포함하는 명세이다.

## 3. 공통 동작 규칙

### 3.1 작업 세션 흐름

1. 사용자가 최초 작업 목표를 입력한다.
2. 작업 시작을 선택하면 FE가 BE에 세션 생성을 요청한다.
3. 생성 성공 후 반환된 sessionId를 활성 세션으로 설정하고 탐색 정보 수집을 시작한다.
4. 분석 대상 페이지가 활성화되면 페이지 정보와 검색어를 수집하고 Page Visit으로 BE에 전달한다.
5. 활성 체류시간과 탭 전환 횟수를 측정하고 방문 기록에 연결하여 전달한다.
6. BE가 저장한 방문을 AI가 3개 Window로 구성하고 BE가 식별·저장·분석 요청 후 최종 상태를 판단한다.
7. FE는 활성 세션의 최종 DRIFT 결과를 받으면 최초 목표를 재제시한다. NORMAL은 알림하지 않으며 TRANSITION은 추가 탐색을 관찰한다.
8. 실제 표시된 알림은 BE에 기록하고 사용자 선택을 alertId에 연결한다. 선택 후 세션은 계속된다.
9. 종료 선택 즉시 수집·알림을 중지하고 POST/PATCH ACK 후 종료 API를 호출한다. 실패 시 END_PENDING으로 복구한다.

고정 주기 평가 조건에서는 설정된 간격으로 최초 목표를 표시하며, 알림 기록과 사용자 선택은 AI 방식과 같은 구조를 사용한다.

### 3.2 목표와 세션 유지

- 최초 목표는 세션 진행 중 분석의 기준으로 유지한다.
- 목표를 변경하려면 현재 세션을 종료한 뒤 새 세션을 시작한다.
- FE에서 이미 활성 세션이 존재하면 새 작업 세션을 동시에 시작하지 않는다.
- 세션 생성 실패 시 수집을 시작하지 않는다.
- 세션 종료 실패 시 즉시 종료된 상태로 처리하지 않으며 오류 안내와 재시도를 제공해야 한다.
- 활성 세션이 없거나 종료된 상태에서는 탐색 정보를 수집하지 않는다.

### 3.3 수집 범위

| 구분 | 대상 및 규칙 |
| --- | --- |
| 분석 대상 | 공개 HTML 문서, 검색 결과 페이지, 기술 문서, 블로그·기사, 공개 논문 및 자료 소개 페이지 |
| 제외 페이지 | chrome://, chrome-extension://, 로그인·회원가입, 결제·금융·개인정보 입력 중심 페이지, Chrome 기본 PDF Viewer |
| 제외 콘텐츠 | 영상·음성 콘텐츠 자체 |
| URL | query parameter와 fragment를 기본적으로 제거한 정규화 URL |
| 본문 | 화면에 표시되는 텍스트에서 script, style, 광고, 숨겨진 요소 및 폼 입력값 등을 제외한 제한된 본문 |
| 본문 길이 | 최대 5,000 Unicode code points (이모지·보충 평면 문자 포함, UTF-16 code units 기준 아님) |
| 활성 체류시간 | 분석 대상 페이지의 탭이 활성이고 브라우저 창도 활성인 시간만 누적 |
| 검색어 추출 | Google Search와 Naver Search의 검색 결과 페이지 |
| 지원 제외 검색 | 다른 검색 서비스 및 웹사이트 내부 검색 |

비밀번호, 폼 입력값, 쿠키, 인증 토큰, LocalStorage·SessionStorage, 클립보드, 전체 키 입력, 마우스 좌표, 다운로드 파일 내용 및 전체 Chrome 방문기록은 수집하지 않는 데이터이다. 검색어는 검색 결과의 URL 또는 페이지 구조에서 추출하며 입력 과정을 감시하지 않는 방식이다.

검색어는 URL의 query parameter를 제거하기 전에 추출한다. 정규화 후 검색어를 복원하거나 임의로 추정하는 방식은 사용하지 않는다.

### 3.4 방문 및 행동 정보

유효 방문은 활성 체류 5초(5,000ms) 이상이며 5초 도달 때 POST 큐에 기록한다. 4초 미만 동일 URL 복귀는 같은 visitId·누적값, 4초 이상은 새 visitId다. 다른 탭 동일 URL·reload·SPA·비활성 시각은 공통 계약 P1 승인 대상이다. 제목·본문은 같은 대상의 성공 캐시를 우선 사용하되 권한·민감 DOM을 다시 검사한다.

5분(300,000ms) 최초 통과·이탈·전환·종료에 누적 행동을 PATCH한다. 탭 전환은 이전 방문에 귀속한다. Window 구성은 AI, ID/저장·최종 판단은 BE다. FE는 직접 최종 상태를 만들지 않는다. 기존 후보 종료 대기와 200개 상한은 변경 대상이며 안전한 영속 전송/복구를 유지한다.

### 3.5 알림과 사용자 선택

- AI 알림은 활성 세션의 최종 분류 결과가 DRIFT인 경우에만 표시한다. Context Model의 중간 상태를 알림 기준으로 사용하지 않는다.
- 분석 실패나 종료된 세션의 지연 응답으로 알림을 표시하지 않는다.
- 알림은 최초 목표를 다시 제시하는 방식이며 현재 페이지를 차단·종료하거나 강제 이동시키지 않는다.
- ‘목표로 돌아가기’는 복귀 의사 기록이다. 특정 페이지로 자동 이동하거나 세션 목표를 변경하는 동작이 아니다.
- ‘계속 탐색’은 현재 페이지 이용과 탐색 분석을 계속하는 선택이다.
- 사용자 선택은 analysisId가 아닌 alertId에 연결하며 실시간 모델 개인화에 사용하지 않는다.
- 실제 표시된 알림만 BE-008에 기록한다. 표시 전 후보나 수신 결과만으로 실제 알림 횟수를 증가시키지 않는다.

## 4. 기능별 상세 명세

### 4.1 FE-001 작업 목표 입력

**대분류:** 작업 세션 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

작업 세션 시작 전에 사용자가 이번 웹 탐색의 목적을 자연어로 입력하는 기능이다. 입력한 문자열은 세션의 최초 목표이며 이후 페이지 내용 및 탐색 흐름의 관련성 분석 기준이다.

목표 예시는 ‘캡스톤 프로젝트에 사용할 공개 인공지능 데이터셋 3개 찾기’와 ‘Spring Boot에서 JWT 인증을 구현하는 방법 조사하기’이다.

#### 동작 조건 및 처리

1. 새로운 작업 세션을 시작하려는 상태에서 목표 입력 영역을 제공한다.
2. 사용자가 입력한 목표의 유효성을 확인한다.
3. 유효한 목표이면 작업 시작 기능을 사용할 수 있도록 한다.
4. 작업 시작 시 목표를 확정하여 FE-002를 통해 BE에 전달한다.
5. 이미 진행 중인 세션의 목표는 새 입력으로 임의 변경하지 않는다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| goal | 사용자가 입력한 최초 작업 목표 |
| createdAt | 원본에 기재된 목표 기준 세션 생성 시각 |

sessionId·startedAt은 BE가 발급한다. 원본 createdAt에 대응하는 별도 목표 필드는 추가하지 않는다.

#### 예외 및 제한사항

- 빈 값이나 공백만 입력한 경우 작업을 시작할 수 없다.
- 목표는 사용자가 수행하려는 작업의 목적을 자연어로 작성하는 방식이다.
- 기존 goalText 5~150자 검증과 앞뒤 공백 정리를 유지한다. 세션 목표는 BE 응답값으로 확정한다.
- 목표 변경은 기존 세션 종료 후 새 세션 시작으로 수행한다.

#### 연관 기능

FE-002 작업 시작, BE-001 세션 생성, AI-001 목표 관련성 계산이다.

#### 완료 조건

- 목표를 입력할 수 있고 빈 값으로는 작업을 시작할 수 없어야 한다.
- 유효한 목표로 작업을 시작하면 기존 공백 정리 외에 의미를 바꾸지 않고 goalText로 전달되어야 한다.

### 4.2 FE-002 작업 시작

**대분류:** 작업 세션 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

입력한 최초 목표로 BE에 세션 생성을 요청하고 성공 시 탐색 정보 수집을 활성화하는 기능이다.

#### 동작 조건 및 처리

1. 유효한 목표가 입력되어 있고 현재 활성 세션이 없는지 확인한다.
2. 사용자가 작업 시작 버튼을 선택하면 BE-001에 세션 생성을 요청한다.
3. 성공 응답의 sessionId를 활성 세션으로 설정하고 시작 정보를 보관한다.
4. 해당 세션의 탐색 정보 수집을 시작한다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| goal | 최초 작업 목표 |
| sessionId | BE에서 생성한 작업 세션 식별자 |
| startedAt | 작업 세션 시작 시각 |

sessionId UUID와 startedAt UTC 밀리초는 BE 발급이다. 시작 동작의 Idempotency-Key는 FE가 생성하고 재시도에서 유지한다.

#### 예외 및 제한사항

- 빈 값이나 유효하지 않은 목표로 시작하지 않는다.
- 이미 활성 세션이 있으면 중복 세션을 시작하지 않는다.
- 생성 요청 실패 시 수집을 시작하지 않고 사용자에게 실패를 안내한다.
- 브라우저 종료 또는 확장 프로그램 실행 상태 변경 시 세션 처리 방식은 복구·비정상 종료 정책에서 정의한다.

#### 연관 기능

FE-001 작업 목표 입력, FE-003 작업 종료, FE-004 페이지 정보 수집, BE-001 세션 생성이다.

#### 완료 조건

- 유효한 목표로 시작을 선택하면 세션 생성 요청이 BE에 전달되어야 한다.
- 생성 성공 시 활성 세션을 설정하고 수집이 가능한 상태로 전환되어야 한다.
- 생성 실패 시 활성 세션으로 전환되지 않아야 한다.

### 4.3 FE-003 작업 종료

**상태:** 기존 END_PENDING/ACK 복구 구현, 정책 유지.

활성 세션이 없으면 종료 요청을 만들지 않는다. 종료 선택 즉시 새 수집·알림을 중지하고 마지막 행동값을 확정한다. IndexedDB에 후보·POST/PATCH·종료 요청을 보존하고 필수 ACK를 모두 영속 확인한 뒤 `POST /api/sessions/{sessionId}/end`를 호출한다. ENDED 확인 후 활성 세션을 정리한다. 현재 FE는 drain 뒤 `{}`를 보내며 BE의 선택 finalBehaviors 원자 처리도 유지한다.

장애 시 END_PENDING을 유지하며 재시도한다. SESSION_ENDED는 데이터 ACK가 아니다. 미전송 원본을 보존하고 충돌로 안내한다. Worker/브라우저 중단·응답 유실·손상 저장소에서 성공으로 추정하지 않는다. 종료 요청 실패가 수집 재개를 뜻하지 않는다. 연관 기능은 FE-002/004/005/006, BE-002/006이다.

완료 조건: 신규 관측 중지와 서버 종료 확인을 분리하고 POST/PATCH→END 순서·재시도 ID/원본·종료 영수증을 보존한다.

### 4.4 FE-004 페이지 정보 수집

**상태:** 수집·HTTP·IndexedDB 구현 있음. #79 경계는 변경 대상.

활성 세션의 허용 페이지를 후보로 관측하고 수집 규격 §2~4에 따라 제목·본문·검색어를 얻는다. 본문 최대 5,000 Unicode code points, 일반 본문 최소50, 검색어+유기 결과1건 이상 기준을 유지한다. EXTRACTION_FAILED는 진단으로 관리하며 정상 방문 POST/Window 수에서 제외한다. 민감 URL·DOM·입력값 차단은 계속 적용한다.

| 필드 | 계약 |
| --- | --- |
| sessionId / visitId | BE 세션 UUID / FE 방문 UUID v4; 복구·재전송에서 유지 |
| browserTabKey | 세션 내 탭 문자열. 방문 ID가 아니며 한 탭에 여러 방문 가능 |
| sequence | 기존 후보 종료 후 발급은 5초 전송과 충돌. 공통 계약 P2의 순서 의미 승인 후 변경 |
| normalizedUrl / domain | Query·Fragment 없는 주소 / 전체 hostname |
| title / content | 성공 캐시 우선 재사용, POST 동결 후 변경 금지 |
| visitedAt / searchQuery / isSearchResultPage | UTC 밀리초 최초 관측 / 일반 null / boolean |
| activeDurationMs / tabSwitchCount / behaviorVersion | 누적 정수 ms / 이전 방문 귀속 횟수 / 단조 증가 버전 |

동일 URL <4,000ms 복귀는 기존 방문, >=4,000ms는 새 방문이다. 같은 탭 A→B→A·다른 탭·reload·SPA·Worker 경계는 P1을 따른다. 저장 URL만으로 다른 검색어나 query 문서를 합치지 않는다. 새 방문에도 캐시를 쓸 수 있으나 개인정보 검증을 생략하지 않는다.

기존 MAX_CANDIDATES=200 중지 대신 지속 수집을 지원하되 ACK 완료 자료 정리·짧은 복귀 캐시와 미완료 큐를 분리한다. 원본/전송 스냅샷/sequence 상한 삭제로 한도를 해소하지 않는다. 전송 후 정책 제외 정정은 P2 선결이다.

완료 조건: 4,999ms 미전송·5,000ms 전송, 3,999/4,000ms 복귀, 캐시와 새 ID 분리, 추출실패 구분, 세션 종료 전 지속 수집, 기존 권한/IndexedDB/ACK 보호 회귀. 연관 기능 FE-002/003/005/006/007, BE-003/009.

### 4.5 FE-005 체류시간 측정

**상태:** active-time 누적 구현 있음. 5초/5분 트리거 추가 필요.

탭과 Chrome 창이 모두 활성인 시간만 누적한다. 다른 탭·앱·최소화·창 비활성·미관측 Worker 구간은 제외한다. 4초 미만 재개는 누적, 4초 이상은 새 방문에서 0부터 측정한다(P1). 예: A 활성6초→다른 탭3초→A 활성2초면 같은 A 방문8초, 다른 탭4초라면 A 새 방문2초로 아직 유효하지 않다.

5초 도달 POST, 최초5분 통과 PATCH, 이탈/탭 전환/종료 최종값 전송이다. 매초 HTTP를 보내지 않는다. 실제 관측값을 보내며 임계값으로 반올림하지 않는다. activeDurationMs와 behaviorVersion은 누적값이고 버전 재시도는 같은 스냅샷이다. 기존10초 분석 대기를 유지하지 않는다. 상세 P3·수집 규격 §5~6.

완료 조건: 누락·중복 이벤트에서도 이중 가산 없음, 300,000ms 통과·POST 이전 PATCH 차단·ACK 유실/복구, 관측 불가 시간 과대 추정 없음. BE가 AI 결과와 함께 상태를 판단하며 체류만으로 FE가 DRIFT를 만들지 않는다. 연관 기능 FE-003/004/006, BE-003/006.

### 4.6 FE-006 탭 전환 감지

**상태:** 이전 방문 귀속 누적 구현, 유지.

A→B 실제 활성 탭 변경은 **A 방문**의 tabSwitchCount를 1 증가시키고 behaviorVersion을 갱신한다. B가 제외 대상이어도 A의 이탈 횟수다. 동일 탭 URL 이동·백그라운드 새 탭·다른 앱 포커스는 전환이 아니다. A 체류 중지, B 측정 시작/재개는 P1 방문 경계에 맞춘다. sessionId+visitId별 누적 정수로 전달하며 세션 총횟수를 각 방문에 복제하지 않는다.

완료 조건: 전환을 이전 방문에 한 번만 귀속, 포커스 중복·탭 닫기 이벤트에서 이중 증가 방지, POST 이후 PATCH 버전 규칙 유지. AI 의미 판단과 분리하여 행동/평가 자료로 보존한다. 연관 기능 FE-004/005, BE-006.

### 4.7 FE-007 검색어 수집

**대분류:** 탐색 정보 수집 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

Google Search 또는 Naver Search 검색 결과 페이지에서 실제 검색어를 추출하는 기능이다. 검색어는 최근 탐색 의도의 변화를 분석하는 Context Model 입력에 사용하는 데이터이다.

#### 동작 조건 및 처리

1. 활성 세션의 현재 페이지가 지원 검색 서비스의 결과 페이지인지 확인한다.
2. URL 또는 검색 결과 페이지 구조에서 검색어를 추출한다.
3. 현재 Page Visit에 연결한다.
4. 검색어 추출 이후 페이지 URL을 정규화한다.
5. FE-004의 방문 데이터와 함께 BE에 전달한다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| sessionId | 현재 작업 세션 식별자 |
| searchQuery | 검색에 사용한 문자열 |
| searchedAt | 검색 결과 페이지 방문 시각 |

wire에는 별도 searchedAt을 추가하지 않고 해당 방문의 visitedAt을 사용한다.

#### 예외 및 제한사항

- 다른 검색 서비스 및 사이트 내부 검색은 초기 지원 대상에서 제외한다.
- 전체 키 입력이나 검색창 입력 과정을 감시하지 않는다.
- 정상 추출할 수 없으면 검색어를 추정하지 않는다.
- 일반 방문의 searchQuery는 null, 검색 페이지 추출 실패는 EXTRACTION_FAILED 진단이며 정상 방문으로 보내지 않는다.

#### 연관 기능

FE-004 페이지 정보 수집, BE-003 방문 기록 저장, AI-002 최근 탐색 흐름 분석이다.

#### 완료 조건

- Google·Naver 결과 페이지에서 검색어를 추출하고 해당 방문과 연결할 수 있어야 한다.
- 지원하지 않는 페이지의 일반 문자열을 검색어로 잘못 수집하지 않아야 한다.

### 4.8 FE-008 목표 이탈 알림 표시

**대분류:** 목표 이탈 개입 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

활성 세션의 최종 분석 상태가 DRIFT인 경우 최초 작업 목표를 다시 제시하는 기능이다. 최종 상태가 NORMAL이면 알림하지 않으며 TRANSITION이면 추가 탐색을 관찰하는 동작이다.

#### 동작 조건 및 처리

1. BE의 analysis-status에서 최종 판단과 알림 후보를 수신한다.
2. 활성 세션에 속한 결과인지 확인한다.
3. BE가 최신 windowId/stateVersion의 DRIFT로 승인한 alert 후보가 있으면 표시한다. result만 보고 후보를 만들지 않는다.
4. 실제 표시 시각을 기록하고 BE-008에 알림 이벤트를 전달한다.
5. FE-009를 통해 사용자 선택을 받는다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| sessionId | 현재 작업 세션 식별자 |
| analysisId / windowId / stateVersion | AI 근거 및 BE 최종 판단 식별자(v2 확장) |
| goal | 최초 작업 목표 |
| finalState | BE의 최종 DRIFT 상태 |
| shownAt | 실제 알림 표시 시각 |

BE가 반환한 AI 유형 alert 후보의 alertId를 이후 shown/사용자 선택에 연결한다. FE가 최종 상태만 보고 새 후보를 생성하지 않는다.

#### 예외 및 제한사항

- 분석 실패 시 표시하지 않는다.
- NORMAL 또는 TRANSITION 결과에 AI 목표 재제시 알림을 표시하지 않는다.
- 종료된 세션에 DRIFT 결과가 늦게 도착해도 표시하지 않는다.
- 이전 세션의 결과를 현재 활성 세션에 잘못 표시하지 않아야 한다.
- 현재 페이지를 차단·종료하거나 강제 이동시키지 않는다.
- 기존 BE의 최소 간격·연속 DRIFT·표시 ACK를 유지하고 v2 stateVersion 연결은 공통 계약 P5를 따른다. UI 형태는 별도다.

#### 연관 기능

FE-009 목표 재제시 후 사용자 선택, BE-007 AI 분석 결과 저장, BE-008 알림 이벤트 저장, AI-003 운영 판단 이관·legacy 비교이다.

#### 완료 조건

- 활성 세션의 최종 DRIFT 결과일 때만 AI 방식의 목표 재제시가 표시되어야 한다.
- NORMAL·TRANSITION·분석 실패·종료된 세션의 지연 결과에서는 AI 알림이 나타나지 않아야 한다.
- 알림 이후 사용자가 다음 행동을 직접 선택할 수 있어야 한다.

### 4.9 FE-009 목표 재제시 후 사용자 선택

**대분류:** 목표 재제시 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

AI 또는 고정 주기 목표 알림 이후 사용자가 원래 목표로 복귀할지 현재 탐색을 계속할지 선택하는 기능이다.

#### 동작 조건 및 처리

1. 현재 세션에서 유효한 목표 재제시 알림이 표시된다.
2. ‘목표로 돌아가기’와 ‘계속 탐색’ 선택을 제공한다.
3. 선택한 action과 선택 시각을 해당 alertId에 연결하여 BE-005에 전달한다.
4. 알림을 종료하고 작업 세션을 계속한다.

| 사용자 선택 | action | 의미 |
| --- | --- | --- |
| 목표로 돌아가기 | RETURN_TO_GOAL | 복귀 의사를 기록하는 선택 |
| 계속 탐색 | CONTINUE_BROWSING | 현재 이용 및 탐색 분석을 계속하는 선택 |

#### 데이터

| 항목 | 설명 |
| --- | --- |
| sessionId | 현재 작업 세션 식별자 |
| alertId | 응답 대상 알림 식별자 |
| action | RETURN_TO_GOAL 또는 CONTINUE_BROWSING |
| selectedAt | 사용자 선택 시각 |

#### 예외 및 제한사항

- 어느 선택에서도 사이트 접근을 제한하거나 특정 페이지로 강제 이동시키지 않는다.
- 사용자 선택으로 현재 모델을 실시간 개인화하지 않는다.
- 같은 알림의 선택 결과를 중복 저장하지 않아야 한다.
- 사용자 평가에서 실제 DRIFT 상태의 RETURN_TO_GOAL 선택 비율을 목표 복귀 선택률 계산에 사용할 수 있다.
- 복귀 선택은 복귀 의사이며 실제 목표 복귀 행동을 확인한 사실과 구분하는 기록이다.
- 기존 BE의 최초 선택 저장·같은 요청 멱등·다른 선택 충돌 계약을 유지한다. 미응답·닫기 UI는 별도다.

#### 연관 기능

FE-008 목표 이탈 알림 표시, FE-010 고정 주기 목표 알림, BE-005 사용자 선택 결과 저장, BE-008 알림 이벤트 저장이다.

#### 완료 조건

- 두 선택 중 하나를 수행하고 해당 alertId에 연결하여 저장할 수 있어야 한다.
- 어느 선택에서도 웹페이지를 강제로 차단하지 않아야 한다.
- 선택 후 작업 세션을 계속할 수 있어야 한다.

### 4.10 FE-010 고정 주기 목표 알림

**대분류:** 사용자 평가 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

AI 페이지 분석과 BE 규칙으로 알림 시점을 정하는 방식의 추가 가치를 비교 평가하기 위해 사전 설정된 일정 간격마다 최초 목표를 재제시하는 기능이다. 최종 서비스의 핵심 목표 이탈 판단 기능과 구분되는 사용자 평가용 기능이다.

#### 동작 조건 및 처리

1. 사용자 평가에서 세션의 알림 조건이 고정 주기 방식으로 설정된다.
2. 작업 세션 시작 후 사전 설정된 간격을 기준으로 알림 시점을 관리한다.
3. 주기가 도래하면 최초 목표를 표시한다.
4. 실제 표시 알림을 BE-008에 기록하고 FE-009에서 선택을 받는다.
5. 다음 주기를 관리하며 활성 세션에서 반복한다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| sessionId | 작업 세션 식별자 |
| goal | 최초 작업 목표 |
| shownAt | 실제 표시 시각 |

알림 기록에서는 FIXED_INTERVAL 유형을 사용하며 analysisId를 연결하지 않는다. 현재 BE 설정의 단일 알림 모드를 유지한다. 최종 평가의 세션별 조건 배정/고정 간격 값은 별도 결정이다.

#### 예외 및 제한사항

- AI 결과와 관계없이 사전에 설정된 주기에 따라 동작한다.
- 고정 주기 간격은 최종 사용자 평가 이전 파일럿에서 AI 방식과 유사한 평균 세션당 알림 횟수가 발생하도록 설정한다.
- 최종 평가 시작 이후에는 간격을 변경하지 않는다. 임의의 분 단위 값을 본 문서에서 지정하지 않는다.
- 세션이 종료되면 해당 세션의 고정 주기 알림도 중단해야 한다.
- 주기 기준 시각, 알림 응답 중 다음 주기 처리, 브라우저 비활성·재실행 상황 및 AI 알림과의 동시 표시 방지 방식은 미확정이다.

#### 연관 기능

FE-009 목표 재제시 후 사용자 선택, BE-008 알림 이벤트 저장이다.

#### 완료 조건

- 고정 주기 평가 조건에서 설정된 간격으로 최초 목표를 표시할 수 있어야 한다.
- 알림 표시 및 선택을 AI 방식과 동일한 구조로 기록할 수 있어야 한다.
- 종료된 세션에 새 고정 주기 알림이 표시되지 않아야 한다.

## 7. 후속 구현과 남은 결정

식별자·단위·종료 ACK·누적값·검색어 null은 수집 규격/공통 계약으로 통일한다. P1(4초 이벤트/SPA), P2(sequence 의미·조기 전송 후 민감 DOM 정정), P3(타이머·장애), P5(버전별 알림) 승인 후 구현한다. UI 형태·최종 평가 고정 간격·비정상 관측의 파일럿 보정·지원 OS 범위는 이번에 임의 확정하지 않는다.

기존 시작 멱등 키, 목표 goalText 5~150자/BE strip, 서버 ACTIVE/ENDED, FE END_PENDING, 권한 요청·철회·명시적 재개, sequence 재사용 방지 및 checkpoint 복구를 보존한다. 원본 createdAt은 세션 startedAt으로, 페이지 측정 시작은 로컬 activeSince로 구분한다. Windows 11 Chrome Stable 보장 범위를 다른 Chromium까지 확대하지 않는다. 후속 수용 케이스는 공통 계약 §12를 따른다.

### #81 FE 구현 계약 보충 — PROPOSED

#83 재검토의 [승인 대장·경계조건](v2-contract-approval.md#4-p1p3-보완-계약과-구현-전-경계)을 함께 따른다. URL 변경과 본문 교체는 독립 검사하고 stale snapshot 세대를 폐기한다. sequence·POST·nextSequence는 한 IDB commit 후 공개하며 v1 checkpoint는 보존한다. 단조시계와 별도로 OS 휴면·미관측 구간을 제외해야 한다.

민감 판정 시 END_PENDING의 일반 원문 drain도 중단한다. 회수 작업은 POST ACK를 기다리지 않는 별도 영속 작업이고, 원문 안전 삭제·최소 영수증 전환·회수 ACK와 종료를 조정하는 개인정보 예외 경로가 필요하다. 이 경로와 서버/AI/Export 회수가 미구현인 상태에서는 5초 조기 POST 운영 활성화가 BLOCKED다.

현재 collector는 1,000ms 유효성, finalized prefix 순서 발급, reload 무조건 재사용을 사용한다. 이번 문서가 제품 동작을 바꾸지는 않는다. [P1~P3 결정안](v2-contract-decisions.md#3-p1--방문-식별과-캐시)은 관측 시점 leftAt/returnedAt과 단조시간 세대, 탭별 대상과 콘텐츠 세대, 방문 병합과 캐시의 분리, 유효화 순서 sequence를 권고한다. 저장 URL만 비교해서는 안 된다.

POST 후 민감정보가 발견되면 [회수 계약](v2-contract-decisions.md#41-전송-후-민감-판정-이미-보낸-자료의-처리)의 별도 작업으로 서버·AI·Export까지 격리하고 삭제한다. ACTIVE 권한 철회의 로컬 삭제만으로 서버 자료가 삭제되지는 않는다. 회수 작업에는 원문 없이 식별자만 남기며 END_PENDING 자료 처리와 구분한다.

Behavior PATCH는 기존 세 필드 그대로 사용한다. 5분 관측이 늦으면 실제 누적값을 보내고 ACK 시각이나 판단 시각을 임계 통과 시각으로 사용하지 않는다. ACK 자료 정리는 현재 endDataDrained의 배열 결합 검증과 충돌하므로 새 checkpoint·영수증 설계 후 시행한다. 진행 중 v1은 v1으로 종료하며 1,000ms snapshot을 5,000ms로 재해석하지 않는다. END_PENDING·서버 종료 충돌·명시적 재개·발급 sequence 상한을 유지한다.

공통 타입은 [PageVisitPost/BehaviorPatch/StatusResponse/CollectionFailure/PrivacyRetraction](contracts/v2/README.md)의 Schema다. status/alert는 기존 DTO를 보존한 v2 projection이며, 일반 searchQuery는 명시적 null, title/content는 필수, 실패 status는 정확히 EXTRACTION_FAILED다. 새로운 표시 허가와 과거 실제 표시의 늦은 ACK를 구분하고, 종료 선택·dirty·PENDING·오래된 후보에서는 표시하지 않는다. FE·BE·데이터 담당 승인 후 구현할 제안이다.
