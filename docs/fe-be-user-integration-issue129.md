## 자유 목표와 v2 생성

1. `POST /api/sessions`는 `goalText`를 strip한 뒤 5~150자로 검증한다. `collectionSpecVersion` 생략은 `1.0`, 허용값은 `1.0`과 `2.0`이다. HTTP filter는 발급된 Bearer/활성 참여자를 확인하고, TLS는 정확히 `test` 프로필의 loopback 예외 외에 필수다. 세션에는 소유자와 유효한 동의 ID가 함께 붙는다. [요청 DTO](../be/src/main/java/com/focusrecovery/domain/session/dto/CreateWorkSessionRequest.java) · [인증 필터](../be/src/main/java/com/focusrecovery/domain/identity/AuthenticationFilter.java) · [생성 로직](../be/src/main/java/com/focusrecovery/domain/consent/OwnedSessionService.java#L20)
2. 정확히 `real-collection` 또는 `individual-local` 프로필이면 자유 목표 경로는 버전 분기 전에 `409 ASSIGNMENT_REQUIRED`다. 해당 프로필의 v2는 배정 소유자·CONFIRMED 목표·유효한 정책/동의·active attempt 제한을 통과한 `POST /api/collection/assignments/{plannedId}/start`로 생성된다. 서버가 목표와 버전을 정하고 Attempt를 같은 트랜잭션에서 기록한다. 정확히 `test` + storage flag에서만 현재 자유 목표 v2를 합성 검증할 수 있다. 기본 프로필은 flag가 켜져도 v2 Storage Gate의 프로필 조건을 통과하지 못한다. 실수집 프로필은 승인·유효 정책과 flag를 함께 요구하며 session–policy 연결과 최신 동의를 계속 확인한다. [프로필/정책](../be/src/main/java/com/focusrecovery/domain/collection/CollectionSitePolicy.java#L35) · [Storage Gate](../be/src/main/java/com/focusrecovery/global/config/V2StorageGate.java#L18) · [배정 트랜잭션](../be/src/main/java/com/focusrecovery/domain/collection/CollectionPlanService.java#L108) · [동의](../be/src/main/java/com/focusrecovery/domain/consent/ConsentService.java#L66)
3. 자유 목표 생성은 참여자 row lock과 참여자 범위로 해시한 키를 쓴다. 같은 키·정규화 목표·버전이면 기존 세션을 201로 반환한다. 바뀐 목표/버전은 422, 키 생략/새 키에는 같은 사용자·같은 목표도 새 세션이 만들어질 수 있다. 일반 생성 경로에는 사용자당 단일 ACTIVE 보장이 없으며 FE의 start guard는 한 Runtime에만 해당한다. 배정 start는 참여자+배정+요청 키로 replay하고 다른 배정에 같은 키는 409다. ## 분석 결과와 알림의 연결

- BE가 v2 Visit을 저장한 뒤 compose dirty/cursor에서 방문 ID·순서 prefix를 고정한다. `V2Dispatcher`가 AI 구성 및 페이지별 관련성 API를 호출하고 BE가 Window/analysis ID와 결과를 저장한다. `WindowDecisionService`는 관련성 label 및 최신 행동 스냅샷에서 뒤쪽 연속 `UNRELATED`를 평가한다. suffix 3 또는 그 suffix에 300,000ms 방문은 DRIFT, suffix 2는 TRANSITION, 나머지는 NORMAL이다. 행동 변경은 상태 버전을 올릴 수 있다. `RAW_ONLY`가 정상적으로 수집돼도 dispatch가 꺼져 있으면 이 분석 상태는 생성되지 않는다. [Dispatcher](../be/src/main/java/com/focusrecovery/domain/analysis/service/V2Dispatcher.java) · [판정](../be/src/main/java/com/focusrecovery/domain/window/service/FinalStateRules.java) · [상태 저장](../be/src/main/java/com/focusrecovery/domain/window/service/WindowDecisionService.java)
- 상태 응답은 `apiContractVersion:2, sessionId, sessionStatus, currentDecision, lastSuccessfulState, alert`와 legacy 호환 요약 두 필드를 반환한다. decision의 공통 필드는 `windowId, windowIndex, analysisId, decisionStatus, stateVersion, finalState, judgedAt, errorCode`다. COMPLETED의 경우 stateVersion·analysisId·finalState·UTC 판정 시각이 채워진다. PENDING/FAILED/INVALIDATED의 stateVersion·finalState·judgedAt은 null, 성공 요약은 이력 참고용이다. Window가 없다면 currentDecision은 null이다. 격리 시 아직 조회 권한/동의가 유효하면 INVALIDATED projection과 빈 성공·알림을 반환할 수 있고, 동의가 철회되면 게이트에서 차단된다. [DTO](../be/src/main/java/com/focusrecovery/domain/analysis/dto/V2AnalysisStatusResponse.java) · [상태 서비스](../be/src/main/java/com/focusrecovery/domain/analysis/service/AnalysisQueryService.java#L63) · [결정 projection](../be/src/main/java/com/focusrecovery/domain/analysis/service/V2AnalysisQueryService.java#L34)
- FE는 위 projection과 호환되며 추가 legacy 필드와 v2 alert의 `windowIndex`를 사용하지 않는다. status용 `V2AlertResponse`는 FIXED의 `analysisId/windowId/stateVersion`을 명시 null로 준다. 고정주기 POST·shown의 일반 `AlertResponse`는 null인 `windowId/stateVersion`을 생략할 수 있어 POST DTO 자체를 status validator에 바로 넣으면 거절된다. [V2 Alert DTO](../be/src/main/java/com/focusrecovery/domain/alert/dto/V2AlertResponse.java) · [일반 DTO](../be/src/main/java/com/focusrecovery/domain/alert/dto/AlertResponse.java) · [FE 검증](../fe/src/v2/status.ts#L30) · [계약 projection](contracts/v2/README.md)
- BE는 최신 구성된 windowIndex와 최신 stateVersion만 후보에 사용한다. 새 Window 생성 및 동일 Window의 dirty/실패는 미표시 후보를 무효화하며, 이전 Window의 늦은 DRIFT는 이력을 남겨도 최신 NORMAL을 덮지 못한다. 또한 연속 DRIFT는 마지막 실제 shown 이후 더 뒤 Window의 정상/전환과 최소 간격(기본 5분)이 있어야 풀린다. `alertId`는 AI의 `windowId + stateVersion`과 연결되고 이 상태의 `analysisId`를 가리킨다. BE의 `createdAt`은 후보 생성, FE의 `shownAt`은 표시 관측, `selectedAt`은 사용자 클릭이다. 선택은 `alertId`당 최초 한 건이다. [후보](../be/src/main/java/com/focusrecovery/domain/alert/service/V2AlertService.java#L45) · [새 Window 무효화](../be/src/main/java/com/focusrecovery/domain/composition/service/CompositionService.java#L143) · [BE 최신성 테스트](../be/src/test/java/com/focusrecovery/domain/integration/V2IntegrationContract.java#L255)

## 화면, Worker 및 환경별 동작

`participant/index.tsx`의 5초 타이머는 visible 및 collectionAllowed일 때 `v2-alert`를 호출한다. `browser.ts`의 Worker는 신뢰된 extension UI URL에서 온 메시지만 받아 후보를 조회한다. UI가 aside를 커밋한 뒤 effect로 `v2-shown`을 보내면 Worker가 후보를 다시 조회한 뒤 일치할 때 `recordShown`으로 IDB에 쓴다. `v2-selection`도 IDB에 먼저 쓴다. 표시 ACK가 없으면 선택 POST에 동일 shownAt을 함께 넣는다. React effect로 확인할 수 있는 범위는 화면 커밋 후 실행까지다. 사용자 열람은 외부 관측이 필요하다. 화면이 후보를 수신한 사실과 BE가 표시·선택을 ACK한 사실도 각각 다른 상태다. [UI](../fe/participant/index.tsx#L44) · [Worker](../fe/src/v2/browser.ts#L203) · [영수증](../fe/src/v2/runtime.ts#L351)

## 중복 지연 종료 복구

| 경우 | 구현과 남은 경계 |
| --- | --- |
| 동일 alertId 반복, 같은 Window/이전 버전 | 이미 IDB에 영수증이 있으면 후보 거절. BE는 최신 Window/버전 및 미표시 후보만 내주고 동일 시각은 replay한다. 저장 전에 두 UI가 조회하면 동일 후보를 각자 그릴 수 있으며, Worker는 영수증을 쓰기 전 표시 예약을 하지 않는다. 이는 코드로 확인했고 실제 2개 화면은 `NOT_VERIFIED`. |
| 이전 세션, 응답 순서, 오래된 상태 | 진행 중 최신 요청 번호와 활성 세션 ID를 비교하고, 상태 JSON의 다른 sessionId는 최종 표시 검증에서 거절한다. 다만 `windowIndex/version`은 Worker 인스턴스에만 있고 세션 세대에 묶이지 않는다. 추가 Vitest는 A의 9번 후보 승인 → B의 1번을 직접 검사하면 유효하나 같은 client에서 null, 또 다른 세션 ID의 9번 JSON을 먼저 넣으면 올바른 1번도 null, 새 client에서는 1번 통과를 재현했다. 문서 재현의 기반은 [status 테스트 Fixture](../fe/tests/v2-status.test.ts)와 [카운터 업데이트](../fe/src/v2/status.ts#L53)다. |
| 분석 실패, 정상 전환, TOCTOU | `lastSuccessfulState`로 DRIFT를 재표시하지 않고 AI 후보는 현재 COMPLETED DRIFT와 식별자가 맞아야 한다. participant의 poll은 null/예외에서 기존 alert state를 비우지 않는다. 렌더 뒤 재조회가 어긋나면 `v2-shown`은 영수증 없이 snapshot을 반환하며 이미 렌더한 UI를 내리지 않는다. UI 전경·세션 세대·후보 변경 확인과 표시 취소, 서버 거절 상태 처리가 필요하다. [poll/effect](../fe/participant/index.tsx#L49) · [재검증](../fe/src/v2/browser.ts#L203) |
| 사용자 클릭 중 종료 | UI stop이 자신의 aside를 지워도 늦은 조회/다른 탭까지 동시에 정리하지는 않는다. `selectAlert`는 접근·격리·로컬 영수증을 검사하지만 lifecycle/stop을 검사하지 않는다. BE는 최초 shown의 유효 시각 및 선택 시계·멱등성을 검사한다. 실제 종료 전 표시의 늦은 ACK와 종료 후 새 표시/클릭을 정책과 상태로 분리해야 한다. [FE 선택](../fe/src/v2/runtime.ts#L362) · [BE 응답](../be/src/main/java/com/focusrecovery/domain/alert/service/AlertDisplayService.java#L81) |
| 표시/선택 ACK 유실, 재시작 | 같은 payload와 타임스탬프를 저장하지만 `flushNotifications`는 전체 루프의 첫 예외에서 멈추고 UI에 ACK 실패를 전달하지 않는다. participant 성공 분기는 서버 확인 없이 aside를 닫을 수 있다. 접근 회복 후 수동 재시도를 할 수 있다. 추가 Vitest에서 `fetch`가 실패하는 합성 Runtime으로 표시·선택 영수증 미ACK → stop/ENDED → 같은 주체로 새 sessionId 시작 → 영수증 배열이 비었음을 확인했다. `drained`는 방문·행동만 포함하고 새 세션이 현재 IDB 상태를 교체한다. ## 비교 평가 연동

현재 BE는 단일 설정 `focus-recovery.alert.mode`로 AI/FIXED를 전환한다. 고정 주기(기본 10분)는 `startedAt + n×interval`, 마지막 시간이 지난 회차만 생성, 이미 표시한 현재 회차는 409다. 기본 모드 AI와 사용자/세션별 코호트는 구분해야 한다. 독립 환경 두 개로 비교 실험을 시작하거나 BE에서 승인된 세션 단위 모드·간격·배정 버전을 고정하는 결정을 먼저 한다. FE는 해당 평가 조건에서만 고정주기 POST를 보내고, 두 모드에 같은 표시/선택 계약을 적용한다. 후보 생성 수, UI/OS 제시 수, 서버가 수리한 shown, 사용자 선택을 따로 집계하며 권한 거부·집중모드·offline으로 생긴 결측도 표시한다.
