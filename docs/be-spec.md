## #89 실제 연동 구현 상태 — 합성 테스트 전용

공식 main `4f9b4fb`의 #85 저장 기반과 #87 AI API를 연결했다. `V2AiClient`는 두 v2 HTTP 응답의 타입·ID·Fingerprint·전체 구성/페이지 대응·시간을 검증하고, `V2Dispatcher`는 영속 dirty/compose/Outbox를 별도 Worker에서 실행한다. 네트워크는 DB 트랜잭션 밖이다. 저장한 AI 결과로 `FinalStateRules`가 `suffix3-v2-proposed.1`을 계산하며, PATCH/finalBehaviors는 포함된 모든 기존 Window를 dirty로 만들어 새 AI 호출 없이 최신 행동으로 재판단한다.

판단·상태 이력·dirty 해제·알림 후보는 같은 세션→Window 잠금 트랜잭션이다. 최신 Window/dirty/PENDING/FAILED/INVALIDATED와 과거 성공 참고값을 분리해 조회한다. v2 후보는 windowId+stateVersion, 실제 shown/response는 기존 alertId 기준이다. V12는 v1 analysisId UNIQUE와 이력을 보존하면서 상태 참조·후보 무효화 시각·지연 재시도 시각을 추가한다.

storage Gate는 그대로이며 dispatcher도 기본false다. 정확히 `test` 프로필+storage/dispatch 두 flag를 명시한 합성 환경만 자동 실행한다. 연결2초·v2 응답130초·Lease180초·저장 여유15초·구성3회/1초·2초 backoff는 개발 한도다. v1 응답10초와 분석 자동 재호출 없음은 유지한다. 운영 승인값이나 모델 실행시간 보장이 아니다.

실제 실행·Mock/실제 HTTP/모델 구분·한계는 [#89 구현 검증](be-ai-v2-integration-validation.md)을 따른다. P1~P6 PROPOSED/P2·P6 BLOCKED, 기본 비활성·운영/실사용자 처리 금지·전체 회수/PURGED 미구현은 유지한다. 아래 #85 단락은 당시 저장 기반의 이력이다.

## 3. 공통 처리 흐름 및 규칙

### 3.1 기본 처리 흐름

1. FE가 최초 작업 목표와 작업 시작 요청을 전달하면 BE-001이 세션을 생성한다.
2. FE가 유효 Page Visit을 전달하면 BE-003이 세션과 연결하여 저장한다.
3. 방문 이후 측정한 활성 체류시간과 탭 전환 정보는 BE-006이 기존 방문에 반영한다.
4. AI가 최근 유효 방문 3개로 구간을 구성하고 BE-009가 검증·ID 발급·저장한다(P4).
5. BE-004가 최초 목표와 탐색 구간을 AI Service에 전달하고 응답을 검증한다.
6. 정상 페이지 분석 결과를 저장하고 BE가 연속 무관 횟수·활성 체류 규칙으로 판단하여 BE-007 상태 이력에 추가한다.
7. 활성 세션의 최종 결과가 DRIFT인 경우 목표 재제시 처리를 수행한다. 사용자에게 실제 표시된 알림은 BE-008이 기록한다.
8. 사용자가 알림에 응답하면 BE-005가 해당 alertId에 선택 결과를 연결한다.
9. 작업 종료 시 마지막 방문의 미반영 행동 정보를 반영할 수 있도록 처리하고, BE-002가 세션을 종료한다.

고정 주기 알림도 실제 표시 시 BE-008에 기록하고 사용자 선택은 BE-005에 저장한다. 해당 알림에는 AI 분석 결과가 연결되지 않는다.

### 3.2 세션 및 데이터 연결 규칙

- 세션의 최초 작업 목표를 해당 세션 분석의 기준으로 사용한다.
- 종료된 세션은 신규 방문을 받지 않는다. 종료 전에 저장된 방문의 구성/분석 backlog는 종료 후 평가용 처리 가능하나 알림은 금지한다.
- 방문, 탐색 구간, 분석 결과, 알림 및 사용자 선택은 해당 작업 세션을 추적할 수 있어야 한다.
- 탐색 구간은 같은 세션의 활성 체류5초 이상·추출 성공 방문3개를 순서대로 포함한다. sequence 의미 변경은 P2 승인 대상이다.
- 동일 URL이라도 실제 별개의 방문이면 각각 다른 Page Visit으로 저장할 수 있다.
- 분석 제외 페이지는 분석용 Page Visit으로 저장하지 않으며 탐색 구간의 방문 개수에도 포함하지 않는다.
- 사용자 선택은 분석 결과가 아니라 알림 이벤트에 연결한다. 이를 통해 두 알림 방식의 반응을 동일한 구조로 기록한다.

### 3.3 분석 실패 및 알림 규칙

- AI 통신 실패, timeout 또는 유효하지 않은 응답을 정상 분석 결과로 처리하지 않는다.
- 분석 실패 시 임의로 NORMAL, TRANSITION 또는 DRIFT를 생성하지 않는다.
- Context Model의 구조화된 출력 검증과 1회 재시도는 AI Service의 책임이다. 재시도에도 실패하면 해당 분석 전체를 실패로 처리하며 목표 재제시 알림을 발생시키지 않는다.
- AI 분석 실패가 사용자의 작업 세션을 중단시키지 않아야 한다.
- 세션 종료 이후 도착한 분석 결과는 평가 목적으로 저장할 수 있으나 새로운 사용자 알림에는 사용하지 않는다.
- 분석 결과 저장과 실제 알림 표시 기록은 별개의 처리이다. DRIFT 결과가 저장되었다는 사실만으로 실제 표시된 알림 수에 포함하지 않는다.

### 3.4 행동 정보와 종료 처리

FE는 5초 도달에 방문 POST, 5분 최초 통과·이탈·전환·종료에 누적 행동 PATCH를 보낸다. 기존10초 분석 대기는 제거한다. 종료 선택 즉시 수집·알림을 중단하고 POST/PATCH ACK 후 END한다. BE 선택 finalBehaviors 원자 처리·ACTIVE/ENDED·종료 멱등은 유지한다. END_PENDING은 FE 상태다. 행동 갱신은 새 Window를 만들지 않고 포함된 기존 Window의 BE 판단을 새 stateVersion으로 보존한다.

## 4. 기능별 상세 명세

### 4.1 BE-001 세션 생성

**대분류:** 작업 세션 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

FE에서 전달한 최초 작업 목표를 기반으로 새 작업 세션을 생성하는 기능이다. 생성된 세션은 이후 방문 기록, 행동 정보 및 AI 분석 결과를 하나의 작업 단위로 연결하는 기준이다.

#### 동작 조건 및 처리

1. FE-002 작업 시작에 따른 세션 생성 요청을 수신한다.
2. 최초 작업 목표가 존재하고 유효한지 검증한다.
3. 유효한 요청이면 새 세션을 생성하고 최초 목표 및 시작 시각을 저장한다.
4. 세션 식별자와 시작 정보를 FE에 반환한다. FE는 해당 식별자를 활성 세션으로 사용한다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| sessionId | 생성된 작업 세션 식별자 |
| goal | 사용자가 입력한 최초 작업 목표 |
| startedAt | 작업 세션 시작 시각 |
| endedAt | 종료 시각이며 생성 시점에는 값이 없는 항목 |

#### 예외 및 제한사항

- 목표가 없거나 공백만 포함되면 생성하지 않는다. 현행 goalText 5~150자·BE strip 검증을 유지한다.
- wire는 goalText이며 시작마다 FE Idempotency-Key를 발급하고 재시도에서 유지한다.
- 동일한 목표 문자열로 여러 개의 독립 세션을 생성할 수 있다.
- 같은 Idempotency-Key+같은 목표는 기존201, 다른 목표는422로 유지한다.

#### 연관 기능

FE-001 작업 목표 입력, FE-002 작업 시작, BE-002 세션 종료, BE-003 방문 기록 저장, AI-001 목표 관련성 계산이다.

#### 완료 조건

- 유효한 최초 목표로 새 세션을 생성하고 목표 및 시작 시각을 저장할 수 있어야 한다.
- 이후 탐색 기록을 연결할 수 있는 세션 식별자를 FE에 반환해야 한다.
- 유효하지 않은 요청으로 세션이 생성되지 않아야 한다.

### 4.2 BE-002 세션 종료

**대분류:** 작업 세션 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

FE의 작업 종료 요청을 처리하고 대상 세션의 종료 시각을 기록하는 기능이다. 종료 후 새 탐색 기록은 거절한다. 종료 전 저장된 방문의 미완료 분석은 후처리 가능하나 새 알림은 금지한다.

#### 동작 조건 및 처리

1. FE-003 작업 종료 요청의 sessionId로 대상 세션을 조회한다.
2. 세션이 존재하고 아직 종료되지 않았는지 확인한다.
3. 마지막 방문의 미반영 행동 정보를 반영할 수 있도록 종료 흐름을 구성한다.
4. 종료 시각을 기록하고 해당 세션을 종료 상태로 처리한다.
5. 종료 결과를 FE에 반환한다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| sessionId | 종료 대상 세션 식별자 |
| startedAt | 작업 세션 시작 시각 |
| endedAt | 작업 세션 종료 시각 |

현행 상태 ACTIVE/ENDED와 서버 UTC 밀리초 endedAt을 유지한다. 원본 endAt은 endedAt으로 통일한다.

#### 예외 및 제한사항

- 존재하지 않는 세션은 종료하지 않는다.
- 이미 종료된 세션에 대한 요청으로 중복 종료 처리를 수행하지 않는다.
- 종료된 세션에는 신규 방문 기록을 추가하지 않는다.
- FE는 필수 POST/PATCH ACK 후 END한다. finalBehaviors가 있으면 행동 반영과 종료는 원자적이며 하나라도 실패하면 롤백한다. 이미 ENDED이면200이고 최초 endedAt을 유지한다.
- 브라우저 강제 종료나 네트워크 단절로 정상 종료 요청을 받지 못한 경우는 별도의 비정상 종료 정책에서 정의한다.

#### 연관 기능

FE-003 작업 종료, BE-001 세션 생성, BE-003 방문 기록 저장이며, 마지막 행동 정보 반영을 위해 BE-006과 연결되는 기능이다.

#### 완료 조건

- 유효한 활성 세션의 종료 시각을 기록하고 이후 활성 세션으로 처리하지 않아야 한다.
- 종료된 세션에 신규 탐색 기록이 추가되지 않아야 한다.
- 존재하지 않거나 이미 종료된 세션에 대한 요청으로 데이터가 잘못 변경되지 않아야 한다.

### 4.3 BE-003 방문 기록 저장

**대분류:** 탐색 기록 관리 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

Chrome Extension이 수집한 분석 대상 페이지 방문을 Page Visit 단위로 작업 세션에 연결하여 저장하는 기능이다. 저장된 방문은 sliding window 구성 및 AI 분석에 사용하는 데이터이다.

#### 동작 조건 및 처리

1. 활성 세션에 대한 분석 대상 Page Visit을 FE에서 수신한다.
2. 세션과 방문 데이터의 유효성을 검증한다.
3. Page Visit을 생성하고 해당 세션과 연결하여 저장한다.
4. AI 구성 작업을 영속화한다(P4). 유효 방문이 3개 미만이면 Window는 없고 분석 대기이며 NORMAL을 생성하지 않는다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| visitId | Page Visit 식별자 |
| sessionId | 작업 세션 식별자 |
| sequence | 방문 순서 |
| normalizedUrl | 정규화 URL |
| domain | 도메인 |
| title | 페이지 제목 |
| content | 최대 5,000 Unicode code points. 현행 nullable, v2는 추출 성공 콘텐츠 필수 |
| searchQuery | 검색어 |
| visitedAt | 방문 시각 |
| activeDurationMs | 누적 활성 체류시간 정수 ms, v2 POST 최소5,000 |
| tabSwitchCount | 탭 전환 행동 정보 |
| isSearchResultPage | 검색 결과 페이지 여부 |

최초 저장 시 확정되지 않은 체류시간과 일부 행동 정보는 BE-006에서 갱신하는 항목이다.

#### 예외 및 제한사항

- 존재하지 않거나 종료된 세션의 방문은 저장하지 않는다.
- 분석 제외 페이지는 분석용 방문 데이터로 저장하지 않는다.
- 본문은 FE와 동일하게 Unicode code point 수로 검증한다. 5,000개 초과 시 HTTP 400 `INVALID_REQUEST`와 `content` 필드 오류를 반환하며 원본을 자동 절단하지 않는다. 저장 컬럼은 기존 `MEDIUMTEXT`를 유지한다.
- FE UUID visitId의 동일 원본 재전송은200, 다른 원본409다. 같은 URL >=4초 복귀는 새 visitId, <4초는 기존 ID다. 다른 탭/SPA 경계는 P1 참조.

#### 연관 기능

FE-004 페이지 정보 수집, FE-005 체류시간 측정, FE-006 탭 전환 감지, FE-007 검색어 수집, BE-006 탐색 행동 정보 갱신, BE-009 탐색 구간 구성이다.

#### 완료 조건

- 유효한 방문을 해당 세션에 연결하여 저장할 수 있어야 한다.
- 방문을 순서대로 조회하고 탐색 구간 구성 및 AI 분석에서 사용할 수 있어야 한다.

### 4.4 BE-004 AI 분석 요청 및 응답 처리

**변경 사유:** 기존 BE 5개 구성·10초 대기·AI 확률 최종 분류를 #79의 AI 구성·BE 규칙 판단으로 변경한다.

P4 권장 흐름은 AI window-compositions 요청 → BE-009 검증/식별/저장 → 기존 /api/ai/analyses v2 요청이다. Window 저장 후 analysisId와 불변 input_snapshot/Outbox를 같은 트랜잭션에서 기록하고 commit 후 V2Dispatcher가 실행한다. 기존 AnalysisExecutor는 v1 전용이다. AI 호출 중 DB 잠금을 유지하지 않는다. 정확한 wire 타입은 공통 계약 §6을 따른다.

- 요청: apiContractVersion=2, analysisId/sessionId/windowId, windowIndex, goalText, position1~3 visits. 실패 추출·5초 미만 입력 금지.
- 응답: ID 일치, 각 position/visitId에 pageResults(label, semanticRelevance, rationale), modelVersions, analyzedAt UTC 밀리초. label은 DIRECT/JUSTIFIED_DETOUR/UNRELATED다.
- BE가 AI 응답을 검증한 뒤 수집 규격 §7의 연속 무관·5분 규칙으로 최종 판단한다. AI 확률은 v2 필수가 아니며 최종 상태를 대체하지 않는다.
- 기존 PENDING/RUNNING claim·완료/실패 보호·queue full·timeout recovery·HTTP/1.1·오류코드 보존. AI 실패를 NORMAL로 바꾸지 않는다. Context 출력 검증1회 재시도는 AI 책임이며 BE 자동 분석 재시도는 현재 없다.
- 중복/지연/역순 결과는 원래 ID에만 기록하고 최신 Window/상태를 뒤로 돌리지 않는다. 종료 후 결과는 저장 가능하나 알림 금지다.

완료 조건: 3개 스키마·소속·버전 검증, 실패 전파·세션 지속·동결 요청 복구, AI 구성과 BE 저장의 멱등. timeout/추가 왕복 예산은 BE·AI 실측 후 승인한다. 연관 BE-007/009, AI-001/002/003.

### 4.5 BE-005 사용자 선택 결과 저장

**대분류:** 사용자 반응 관리 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

AI 방식 또는 고정 주기 방식의 목표 재제시 알림에 대한 사용자 선택을 해당 알림 이벤트와 연결하여 저장하는 기능이다. 두 알림 방식의 사용자 반응을 동일한 구조로 평가하기 위해 analysisId가 아니라 alertId를 연결 기준으로 사용하는 기능이다.

#### 동작 조건 및 처리

1. 유효한 알림에 대한 사용자 응답을 FE에서 수신한다.
2. alertId로 알림 존재 여부를 확인한다.
3. 선택 값을 검증한다.
4. 선택 결과를 해당 알림 및 세션과 연결하여 저장한다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| feedbackId | 선택 결과 식별자 |
| sessionId | 작업 세션 식별자 |
| alertId | 대상 알림 이벤트 식별자 |
| action | RETURN_TO_GOAL 또는 CONTINUE_BROWSING |
| selectedAt | 선택 시각 |

#### 예외 및 제한사항

- 존재하지 않는 알림에 대한 선택은 저장하지 않는다.
- 동일 alertId에 대한 선택 결과가 중복 생성되지 않아야 한다.
- 기존 최초 선택 저장·같은 요청 멱등·다른 선택 충돌 규칙을 유지한다. 미응답/닫기 UX는 별도다.
- 사용자 선택은 실시간 모델 개인화에 사용하지 않는다.

#### 연관 기능

FE-009 목표 재제시 후 사용자 선택, BE-008 알림 이벤트 저장이다.

#### 완료 조건

- 사용자 선택을 해당 목표 재제시 알림에 연결하여 저장할 수 있어야 한다.
- AI 알림과 고정 주기 알림에 동일한 데이터 구조를 사용할 수 있어야 한다.

### 4.6 BE-006 탐색 행동 정보 갱신

visitId가 path의 sessionId에 속하는지 확인한다. activeDurationMs:int64, tabSwitchCount:int32, behaviorVersion:int64 누적값을 받는다. 기존 잠금·버전 규칙을 유지한다. 낮은 버전은 applied=false/현재 ACK, 같은 버전 같은 값은 멱등, 같은 버전 다른 값409, 높은 버전 누적값 감소409다. 탭 전환은 이전 방문 귀속이다.

5분 최초 통과(old<300000<=new), 이탈·전환·종료 값이 반영되면 해당 방문을 포함하는 모든 기존 Window의 BE 판단 입력을 갱신한다(P3/P5). 새 Window·AI 재호출을 만들지 않는다. AI 미완료면 대기 후 최신 행동으로 판단한다. POST ACK 이전 PATCH·종료 후 PATCH는 허용하지 않는다. 매초 전송 방식은 사용하지 않는다.

완료 조건: 잘못된 세션 갱신 차단, 역순/중복/동시 PATCH 보호, 5분 갱신과 동일 Window 버전 이력, finalBehaviors 원자 종료. 연관 FE-003/005/006, BE-002/003/004/007.

### 4.7 BE-007 AI 결과 및 최종 상태 이력 저장

**변경 사유:** AI 원본 예측과 BE의 시간 의존 최종 판단을 분리한다. 기존 요구인 확률·분석 입력 재현은 legacy 데이터에서 유지한다.

analysis_result의 analysisId/windowId, input_snapshot, 처리 상태, 오류, AI page_results, model_versions/analyzed_at을 보존한다. 체류 갱신으로 원본을 덮지 않는다. v2 pNormal/pTransition/pDrift는 nullable legacy 정보이며 BE 판단 근거가 아니다.

window_state_history에는 windowId+stateVersion PK, analysisId FK, judgedAt, ruleVersion, finalState, 방문3개별 activeDurationMs/tabSwitchCount/behaviorVersion, inputFingerprint를 저장한다. append-only이며 같은 입력 재처리는 기존 버전, 다른 입력은 결과가 같아도 새 버전이다(P5). 상태 조건 순서는 수집 규격 §7을 따른다. AI 실패/누락은 성공 이력을 만들지 않고 decisionStatus/errorCode/finalState=null로 조회한다.

예: [DIRECT,DIRECT,UNRELATED]에서 W1 v1 P3=5000 NORMAL, v2 P3=300000 DRIFT. 같은 windowId·analysisId, 다른 stateVersion이다. 과거 버전은 당시 스냅샷으로 재현한다. 현재 상태는 최신 Window의 최신 버전이며 과거 지연 응답/체류 갱신으로 되돌리지 않는다.

기존 analysis-status/list/detail 경로·페이지네이션을 유지하고 v2 필드와 이력 조회를 확장한다(공통 계약 §3, §7). 사람 정답은 별도 라벨 저장소이며 result에서 복사하지 않는다. 완료 조건: 근거별 시점 재현·버전 멱등·지연/역순 보존·정답 분리. 연관 BE-004/006/008/009.

### 4.8 BE-008 알림 이벤트 저장

**대분류:** 알림 관리 / **상태:** 기존 구현 범위는 공통 계약 §2 참조; #79 변경은 후속

#### 기능 설명

사용자에게 실제 표시된 목표 재제시 알림의 종류와 표시 시각을 기록하는 기능이다. 알림 횟수 및 사용자 선택 평가를 위해 실제 표시된 알림을 독립 이벤트로 관리하는 기능이다.

#### 동작 조건 및 처리

1. FE에서 실제 목표 재제시 알림이 표시된다.
2. 알림 방식과 세션을 확인한다.
3. AI 알림이면 최신 Window의 유효한 BE DRIFT stateVersion과 연결하고 analysisId도 근거로 보존한다.
4. 고정 주기 알림이면 분석 결과 연결 없이 저장한다.
5. 알림 이벤트를 저장하고 alertId를 반환하여 이후 사용자 선택과 연결한다.

#### 데이터

| 항목 | 설명 |
| --- | --- |
| alertId | 알림 이벤트 식별자 |
| sessionId | 작업 세션 식별자 |
| alertType | AI 또는 FIXED_INTERVAL |
| analysisId | AI 알림의 관련 분석 결과 식별자이며 고정 주기 알림에는 없는 항목 |
| shownAt | 사용자에게 실제 표시된 시각 |

#### 예외 및 제한사항

- AI 알림은 유효한 BE DRIFT 판단에 연결한다. 후보 생성·조회·shown 직전 모두 최신 windowIndex/stateVersion, ACTIVE와 기존 최소 간격·연속 DRIFT 규칙을 재확인한다.
- 고정 주기 알림에는 analysisId가 존재하지 않는다.
- 같은 알림 이벤트를 중복 저장하지 않아야 한다.
- 알림 후보 생성이나 전송만으로 실제 표시 이벤트를 기록하지 않는다.
- 기존 analysis-status의 alert 후보, shown API와 alertId 중복 방지를 유지한다. v2 작업/후보의 키는 windowId+stateVersion으로 확장하는 P5 승인 대상이다.
- 기존 설정·연속 DRIFT 보호를 유지하며 같은 Window 내 상태 전환의 리셋 조건은 P5 검토 대상이다. 고정 주기 평가 간격은 별도 파일럿 결정이다.

#### 연관 기능

FE-008 목표 이탈 알림 표시, FE-010 고정 주기 목표 알림, BE-005 사용자 선택 결과 저장, BE-007 AI 분석 결과 저장이다.

#### 완료 조건

- 두 알림 방식을 구분하여 저장할 수 있어야 한다.
- 실제 표시된 알림 횟수를 세션 단위로 계산할 수 있어야 한다.
- 사용자 선택 결과를 개별 알림과 연결할 수 있어야 한다.

### 4.9 BE-009 탐색 구간 구성 검증·식별·저장

**ID 유지·책임 변경:** 멤버 구성 주체는 BE에서 AI로 이전한다. BE는 AI 구성 결과 검증, UUID windowId·세션 windowIndex 발급, analysis_window/window_visit 저장·중복/순서 보호를 담당한다. 단순히 BE WINDOW_SIZE를3으로 바꾸는 구현은 새 책임 계약을 충족하지 않는다.

P4의 구성 커서·입력 스냅샷·응답 검증/CAS 후 Window를 저장하고 기존 분석 요청 흐름으로 연결한다. 3개 미만은0개, n개면 max(0,n−2)개다.

| 유효 방문 | 구성 주체 AI의 새 구간 | BE 저장 누계 |
| --- | --- | --- |
| P1~P2 | 없음 | 0 |
| P1~P3 | [P1,P2,P3] | 1 |
| P1~P4 | [P2,P3,P4] | 2 |
| P1~P5 | [P3,P4,P5] | 3 |

sequence 공백을 허용하고 오름차순의 인접한 유효 방문3개를 사용한다. windowIndex는 별도 생성순서다. 기존 Window는 재구성하지 않는다. 신규 방문 역순 차단은 마지막 Window 경계만이 아니라 구성 watermark로 보호해야 한다. 이미 저장된 같은 원본 재전송200은 유지한다. 중복 구성은 기존 windowId를 반환하고 Window/분석을 추가하지 않는다. 체류 변경은 Window 생성 사유가 아니다.

완료 조건: AI가 멤버를 구성한다는 경계 검증, 소속/순서/3개·stride1·누락·중복 검사, 구성 실패 커서 미전진, 세션 잠금/CAS·DB UNIQUE, 기존5개 Window 보존. 연관 BE-003/004/007, AI-002.

## 5. 공통 데이터 관계

다음은 논리적 연결 관계이며 실제 테이블 구조 및 제약 조건은 ERD에서 확정하는 사항이다.

| 데이터 | 연결 대상 | 연결 기준 및 의미 |
| --- | --- | --- |
| 작업 세션 | 최초 목표 | 세션의 goal을 분석 기준으로 유지하는 관계 |
| Page Visit | 작업 세션 | sessionId로 방문이 속한 작업을 식별하는 관계 |

| AI 분석 결과 | 작업 세션, 탐색 구간 | sessionId 및 windowId로 분석 대상을 추적하는 관계 |

분석 결과의 startVisitId·endVisitId는 windowId가 가리키는 구간과 일치해야 한다. 실제 구현에서 구간 경계값을 결과에 중복 저장할지 구간 조회로 제공할지는 ERD 단계에서 확정하는 사항이다.

실제 DRIFT 최초 발생 구간은 평가용 정답 라벨에서 확인할 정보이며, 저장된 예측 결과만으로 확정할 수 있는 정보가 아니다. BE-007과 BE-009는 예측 결과와 분석 구간을 추적할 수 있도록 지원하는 기능이다. 정답 라벨 연결·독립 투표·Export 구조는 공통 계약 §9의 P6 제안이며 승인 후 구현한다.

## 8. 구현 전 승인·후속 범위

공통 계약 P2(sequence·조기 전송 후 개인정보), P4(AI 구성→BE 저장→분석), P5(상태/알림 버전), P6(라벨/Export)가 관련 담당자 승인 대상이다. 기존 API의 타입·단위·버전·종료/중복 처리는 공통 계약 §3, DB 변경 전후와 Flyway expand/검증/신규 세션 활성화는 §8을 따른다. 기존 V1~V10 수정/실행은 이번 범위 밖이다.

구현 검증은 기존 테스트를 보존하면서 5초·3개·5분·오류 null·상태 이력/역순·legacy 전환 케이스를 추가한다. 전체 수용 기준은 공통 계약 §12다. UI 형태·최종 평가 간격·미관측 종료 정책은 별도 결정이며 임의 값을 지정하지 않는다.

### #81 BE 구현 계약 보충 — PROPOSED

#83의 [비동기 일관성 보완](v2-contract-approval.md#6-p4p5-비동기-일관성-보완)을 따른다. 구성 입력의 불변 prefix·privacy revision과 cursor CAS를 분리하여 append/PATCH가 구성 job을 불필요하게 취소하지 않게 한다. 판단은 commit 시 최신 행동 벡터 확인이 필요하다. 시작 멱등키의 목표+규격 버전, finalBehaviors의 dirty 처리, durable outbox를 검증한다.

개인정보 tombstone/세션 격리는 원본 replay보다 먼저 검사한다. 회수 중 currentDecision은 가능한 경우 INVALIDATED, lastSuccessfulState/alert는 null이며 Window가 없더라도 분석/공유를 차단한다. PURGED는 Export/학습/백업 영향까지 증거가 확인된 집계 상태다. 현행 FK/인증/API로 완료된 기능이 아니며 [회수 검토](v2-contract-approval.md#5-p2-개인정보-회수의-단계별-차단)의 신규 저장·권한·삭제 구현이 필요하다.

[결정안 P2/P4/P5](v2-contract-decisions.md#6-p4--ai-구성과-be-저장)에 따라 수신 lastAcceptedSequence와 구성 composedThroughSequence를 분리한다. 권장안은 첫 Window 이전부터 신규 sequence의 단조 증가를 요구하고 숫자 공백을 허용하며, 개인정보 tombstone/격리 검사 후 비철회 같은 원본 replay를 처리하는 방식이다.

AI 구성 요청은 본문 없이 ID/sequence의 직전 최대 두 방문과 신규 prefix를 보낸다. 1~2개 입력에서도 커서를 전진시킨다. 별도 compose job에는 session FK만 두고, 트랜잭션 밖에서 HTTP를 호출한 뒤 세션 잠금/CAS로 Window·분석 PENDING·outbox·커서를 원자 저장한다. V4 Window FK 확보 전에는 분석행을 저장할 수 없다. 구성 실패 시 커서는 불변이며 v2에는 기존 10초 대기를 적용하지 않는다. v1은 그대로 유지한다.

행동 변경은 해당 방문을 포함하는 기존 Window 최대 세 개를 dirty로 만들고, 고정 AI 결과로 재판단한다. 실제 판단 입력 변경마다 stateVersion을 추가한다. 같은 Window의 DRIFT 버전 증가만으로 반복 표시하지 않고, 기존의 뒤 Window 복귀 조건과 shownAt 최소 간격을 유지하도록 권고한다. 실제 표시의 늦은 기록은 새로운 후보 허가와 구분한다. V6 UNIQUE(analysis_id)와 V7 PK(analysis_id)는 상태별 후보와 충돌하므로 신규 키/FK 이관이 필요하다.

[Schema](contracts/v2/README.md)의 필수·null·오류·조회 projection을 FE·AI와 공통 사용한다. 현재 Window가 pending/failed/invalidated 또는 dirty이면 finalState=null이고 과거 성공은 참고 필드다. 회수는 ENDED에서도 소유권 검증 후 가능하도록 제안하지만 현재 인증 체계와 FK로는 단순 DELETE가 불가능하다. tombstone·파생 무효화·원문 회수 작업이 선결이다. 기존 V1~V10·운영 DB·제품 코드 변경은 없다. BE·AI·FE·개인정보 담당 승인 후 신규 migration과 호환 검증을 수행한다.
